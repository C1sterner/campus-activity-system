# 校园活动报名审核系统构建准备与协作建议

本文件为上轮完整工程建议。2026 年 11 月 23 日起，课程项目当前范围、实名分工和三周日程以第 08 至 10 号文档为准。

日期：2026 年 11 月 23 日。面向第 23 组四位成员。

建议建立一个共享 Git 仓库，并采用“一人负责集成、四人分工、全员可用 AI”的方式。这个系统规模适合模块化单体应用。一名熟悉 Java、Vue、数据库和部署的成员，有可能借助 AI 完成大部分编码，但能生成代码并不等于已经完成需求核对、并发控制、权限检查、测试、部署和答辩准备。不能仅凭两份说明书给出可信的 AI 完成比例或工期承诺。

准备包已把需求整理为实施基线，提供六表 SQL 草案、接口约定、任务依赖、验收计划和协作模板。正式编码前仍需由小组裁定文档冲突并锁定依赖版本。

## 1 项目范围与实现顺序

需求规格 V1.2 第 3.2 节定义九个用例，四类角色为 student、activity_admin、teacher、admin，数据库为六张表。

| 阶段 | 建议内容 | 验收产物 |

| 第一条完整流程 | 登录，活动发布，学生报名，指定教师审核，学生查询 | 使用真实数据库完整演示一条业务链 |

| 活动管理员数据范围待确认 | 需求 2.3.3；设计 A7 | 统计、列表、导出可能出现权限不一致 | 按需求暂拟可看全部正式报名；管理操作仍限定本人活动，最终组内裁定 |
| 文件 20MB 与请求体 20m 混用 | 需求 1.5；设计 7.1 | 恰好 20MB 的合法文件因 multipart 开销被 Nginx 拒绝 | 文件上限暂定 20MiB，请求总上限 22MiB，三层一致 |
| 流式写文件却先查出全部记录 | 设计 5.3.6 | 写出流式仍可能让 JVM 内存耗尽 | 数据读取也要游标或分批，限定同一筛选口径与导出上限 |
| 数据变更成功但日志失败需降级 | 需求 3.3.8；设计 5.3.7 | 在同一事务中捕获异常未必能阻止整体回滚 | 主业务提交后使用独立日志事务，配置可验证的告警通道 |
| H2 不能证明 MySQL 行为正确 | 设计 7.6 | JSON、索引、事务与并发行为可能不同 | 核心集成测试使用独立 MySQL 8.0 测试库 |

另外，驳回后能否重新提交、附件丢失后的补传流程、活动发布后修改表单或更换教师、用户删除和外键保留策略，均需要在对应模块开发前明确。

## 3 技术方案与工程布局

采用一个后端应用、一个前端应用、一个 MySQL 库，加 Nginx 和受控文件目录。当前规模没有证据需要微服务、消息队列、Kubernetes 或复杂分布式事务。后续通过业务量与压测结果决定是否增加组件。

调用路径建议为：Vue 页面 → HTTP Controller → Service 业务事务 → MyBatis Mapper 或 DAO → MySQL。设计中的业务控制类职责可落到 Service，HTTP Controller 负责入参、认证上下文和响应转换，并在设计追踪表中保留原类到实现类的对应关系。不能为复制类图机械添加大量无用接口，也不能把业务规则放在 Mapper 内。

数据库实体仅在后端内部使用；外部响应使用 DTO，严禁把 User.password、附件磁盘绝对路径或任意配置值直接序列化返回。这是对设计“PO 跨层传递”的实现补充。

| 项目 | 文档现状 | 建议基线与动作 |
| --- | --- | --- |
| JDK 与 Spring Boot | JDK 1.8+；Boot 2.7 为设计 A1 假设 | 新建项目建议 JDK 17 与兼容的 Boot 3.x 版本；选择时核对维护状态和兼容矩阵并锁定补丁号。若课程要求 Boot 2.7，单独记录保留原因及风险 |
| 持久化 | MyBatis、MySQL 8.0 | 保留，集成测试使用真实 MySQL；迁移 SQL 单向版本化 |
| 前端 | Vue 3、Element Plus 为 A1 假设 | 保留 JavaScript，使用 Vite；选定兼容的 Node LTS 和具体依赖版本，提交锁文件 |
| 浏览器 | Chrome 90、Edge 90、Firefox 88 及以上 | 当前 Vite 默认产物未必覆盖这些低版本，应明确 build.target 并实测；若修改浏览器下限须登记变更 |
| 认证 | A2 仅规定 token | 推荐单实例先用服务端可撤销的随机 token；传 Authorization 头，过期、退出、停用和改密失效都要实现。若选择 JWT，另补撤销方案 |
| 密码与验证码 | 加盐哈希，图片验证码 | 使用 BCrypt；验证码 ID 与服务端状态关联，一次有效、有过期和尝试上限；公开注册强制 student |
| 文件 | 本地目录，jpg/png/pdf，20MB | 目录放 Web 根目录之外，随机文件名；大小、扩展名、MIME 和文件头共同检查；授权后读取 |
| 测试与构建 | 尚无工程版本和流水线 | Maven Wrapper、前端 lockfile、后端测试、前端构建和少量关键页面流程测试 |

这是技术提案。准备包未创建依赖清单或伪造锁文件，未将新技术方案冒充原文要求。正式建立工程时必须把“17”“3.x”等范围替换为经过构建验证的具体版本。

## 4 数据与并发准备

已按两文档的六表结构整理 SQL：sys_user、activity、registration、review_record、sys_config、operation_log。保留原状态编码，避免前后端分别发明枚举。

最关键的两个约束是 registration 的 `(activity_id, user_id)` 唯一索引，以及审核时同时判断主键、version 与待审核状态。审核状态更新和 review_record 插入必须同一事务提交；插入记录失败时状态也必须回滚。

还需覆盖容易被 AI 漏掉的情况：两个并发请求同时把同一条草稿转为报名；断网恢复的旧草稿覆盖已提交数据；上传完成但报名事务失败留下孤儿文件；用户停用或角色变化后旧 token 继续访问；修改表单导致历史答案无法解释。具体要求见接口、决策和事务说明。

SQL 中增加的 CHECK、受限删除外键和配置初值均为实施建议。它们已经标注，并未在本机现有数据库执行。

## 5 Git 仓库的必要性与最低协作规则

对四人小组，建议把共享 Git 仓库作为开工条件。Git 是本地版本管理工具；GitHub、Gitee 等托管平台提供共享远程仓库和评审。只有本地 Git 不能实现组内共享备份。

| 场景 | Git 的具体价值 |
| --- | --- |
| 四人同时修改 | 分支隔离变更，通过 PR 发现同一接口、字段或文件的冲突 |
| 一人主写且大量使用 AI | 在每次 AI 修改前后形成小提交，可定位和回退错误改动 |
| 课程验收与交接 | 需求、实现、测试和评审可以对应到任务和提交记录 |
| 演示前出现回归 | 使用已通过验收的标签恢复版本，避免靠“最终版 3”压缩包找代码 |
| 成员临时无法参与 | 其余成员能克隆、构建并接手，降低单人依赖 |

采用一个仓库存放 frontend、backend、db、deploy、docs。主分支 `main` 随时保持能构建；短期功能分支 `feat/TVA006-registration`、`fix/review-conflict`；每个 PR 只解决一个可验收问题，至少另一名成员评审。四人小组通常不需要长期 develop 分支或完整 Git Flow。

平台允许时保护 main：禁止直接推送，要求一名评审，待流水线建立后要求测试与构建通过。平台或套餐不支持时用组内规则执行，不把设置存在与否当作功能保证。数据库迁移只追加，新迁移由一人负责编号；已有迁移被别人执行后不可随意重写。

不要提交 `.env`、真实密码、token、上传材料、数据库数据目录或日志。Git 不替代数据库和附件备份。原 DOCX 适合留存基线快照，日常需求差异与决策用 Markdown，避免多人同时编辑 Word 造成难合并的二进制冲突。

准备目录初始化本地 Git，不配置远程仓库、不上传文件。远程仓库由小组确定平台后建立并邀请成员，见 CONTRIBUTING.md。

## 6 四人分工建议

成员 A—D 是待认领职责，不代表已给四位同学分配角色或评价能力。

| 职责 | 主责工作 | 必须有的交付证据 | 交叉评审 |
| --- | --- | --- | --- |
| A 核心业务与集成 | 报名、审核、数据约束、事务、发布整合 | 并发报名与审核测试，完整业务链 | 由 D 验收；B 评审接口可用性 |
| B 前端与体验 | 角色菜单、动态表单、草稿、审核与管理页面 | 页面流程、断网恢复、错误提示 | 由 C 评审权限相关交互 |
| C 平台与后台 | 登录注册、授权、账号配置、文件服务、导入导出 | 越权、停用失效、文件边界测试 | 由 A 评审安全与事务 |
| D 验收与交付 | 用例追踪、集成测试、环境、部署、备份恢复、说明书修订 | 测试报告、复现脚本、发布说明 | 由 A 复现部署，B 复核演示 |

D 应承担可复用脚本、测试或报表等实际工程任务，并与 C 分担统计导出验收；不宜只在最后整理文字。A 的备份集成人建议由 C 担任。每人至少能在自己的机器运行系统，并解释一次报名与一次审核的权限、状态和事务行为。

## 7 一人借助 AI 能否完成大部分项目

对本系统，大量工作是常见页面、CRUD、DTO、Mapper、校验器和测试骨架，适合 AI 辅助。熟悉整体技术栈的人可以承担大部分代码生成与整合；对刚入门的人，AI 也可能同时引入权限漏洞、错误事务边界和难以理解的依赖问题，未必更快。代码行数不能作为完成率。

| 组织方式 | 适用条件 | 主要代价 | 本项目建议 |
| --- | --- | --- | --- |
| 一人加 AI 完成全部 | 很小的演示、个人练习，且一人能调试全栈 | 测试和代码由同一人判断，进度与知识集中 | 可做原型或赶进度时主写，不宜作为四人最终交付的唯一安排 |
| 四人各做一套再拼接 | 接口和数据未先统一 | AI 容易生成四种风格、重复认证和不兼容字段 | 应避免，先共同冻结契约再分支开发 |
| 一人集成 四人分责 全员 AI | 有统一接口、数据结构和验收标准 | 需要短评审与持续集成 | 推荐，保留编码效率并提高独立验证与交接能力 |

每次交给 AI 的任务应写明用例、允许修改目录、输入输出、状态编码、权限、失败行为和验收用例。让 AI 先报告与基线不一致之处；小步生成，运行测试，人工查看差异，再提交。另一名成员负责验证关键规则，不能把“AI 说已测试”作为证据。

可直接使用的任务示例：

> 实现 TVA007 审核提交。遵循 docs/03 接口草案和 db/review-transaction.md，只修改后端审核模块和对应测试。教师必须为活动指定教师，result 1 映射报名状态 2，result 2 映射状态 3 且原因去空格后非空。更新必须同时判断 regId、version、status=1，成功后 version 加一，并与审核记录插入处于同一事务。提供并发审核仅一次成功、插入记录失败回滚、非指定教师拒绝三个真实 MySQL 测试。列出实际运行的命令及结果，未运行须明确标注。

## 8 开工与交付门槛

开工前：明确功能范围、注册方式、数据范围、附件规则、动态表单协议、版本选择、时间边界；分配负责人和评审人；四人能使用同一仓库；能在隔离数据库创建表并验证约束。

每个功能合并前：接口已对齐，成功和失败路径可复现，数据级权限通过，未泄漏实体字段，测试命令和结果可查，需求与设计文档同步更新。

发布前：九个用例验收完成，核心并发和边界检查通过，数据库与附件可恢复，另一成员从干净目录能够按说明构建和部署，发布 commit 与标签明确。

需求中的 2 秒、100 并发或每秒 100 请求、每日万人次和 99.9% 可用性目前只是目标。必须明确负载模型、数据量、观察周期与统计口径后验证；单机演示或一次压测不能证明长期 99.9% 可用。详细测量提案见测试计划。
