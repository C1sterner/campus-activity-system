# 事务与并发实现约束

## 审核

在一个数据库事务中执行：

```sql
UPDATE registration
SET status = :new_status, version = version + 1, update_time = CURRENT_TIMESTAMP
WHERE reg_id = :reg_id AND version = :version AND status = '1';
```

影响行数为 0 时回滚并返回 `CONFLICT_409`。影响行数为 1 时插入 `review_record`，插入失败必须回滚报名状态。审核前还要用服务端身份确认 `activity.reviewer_id = current_user_id`。

## 报名

草稿和正式提交共用 `(activity_id, user_id)` 唯一记录。已有草稿时使用带 `status='0'` 的条件更新，成功提交令 `status='1'`、`version=version+1`、`submit_time=NOW()`；影响行数为 0 时重查状态并拒绝重复提交。不能用“先查到草稿，再无条件 UPDATE”的方式，否则并发请求会覆盖正式报名。

无记录时可以插入待审核行，由唯一索引兜底。并发重复键需要重查：若另一请求仅刚创建了草稿，可尝试一次草稿条件提交；若已是正式报名则返回 `DUPLICATE_409`。自动暂存只允许插入新草稿或条件更新 `status='0'` 的行。使用原子 upsert 时每个待修改字段都必须以状态为条件，禁止覆盖正式记录。

审核资格检查和状态更新应在同一事务读取活动分配。首版发布后不允许更换审核教师（D10）；若将来支持更换，应对活动行加锁并统一锁顺序，防止旧教师在分配变更后仍提交。

## 文件孤儿清理

文件写入和数据库事务不是天然原子操作。建议先写临时随机文件并完成校验，将其原子移动到同一磁盘的最终随机路径，再开启短数据库事务引用该最终路径。数据库写入失败时删除本次新文件；删除失败记录待清理项。不要采用“数据库已经提交成功，再把临时文件改名”的顺序，否则改名失败会让成功报名指向缺失材料。

进程可能在文件移动后、数据库提交前崩溃，仍会留下无引用文件。定期清理应比对数据库引用、排除正在上传的文件、设置超过最大请求时长的宽限期，并记录删除清单。文件存放于 Web 根目录之外，仅通过授权流接口读取。草稿是否持久化文件遵循 D08。
